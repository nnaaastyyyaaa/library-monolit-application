# Звіт з лабораторної роботи №5: Модульний моноліт

## 1. Аналіз архітектури модульного моноліту

### Визначення обмежених контекстів (Bounded Contexts)
В рамках лабораторної роботи систему було розділено на два ключові модулі, що представляють окремі обмежені контексти:

1.  **Core (Основний контекст):** Відповідає за основну операційну діяльність бібліотеки: управління книгами, користувачами, категоріями та процесом резервації. Це ядро системи, де зосереджена бізнес-логіка, реалізована в попередніх роботах.
2.  **Analytics (Аналітичний контекст):** Відповідає за збір та агрегацію статистичних даних, таких як кількість резервацій книг. Цей модуль є "споживачем" даних і працює незалежно від операційної логіки основного модуля.

### Ізоляція модулів та публічні контракти
* **Фізична ізоляція:** Кожен модуль має власну внутрішню структуру шарів: `domain`, `application`, `infrastructure` та `presentation`.
* **Публічний контракт:** Взаємодія між модулями обмежена. Модуль `Analytics` не має прямого доступу до репозиторіїв або сутностей `Core`. Єдиною точкою входу для даних є обробники подій (Event Handlers).

### Anti-Corruption Layer (ACL)
Щоб захистити доменну модель модуля `Analytics` від змін у структурі `Core`, було впроваджено шар ACL:
* **Мапери:** Використовується `analyticsMapper.js`, який транслює дані зовнішніх подій у внутрішній формат аналітики.
* **Захист:** Навіть якщо структура сутності `Book` у модулі `Core` зміниться, це потребуватиме лише оновлення мапера в `Analytics`, не зачіпаючи його внутрішню логіку підрахунків.

### Стратегія узгодженості (Consistency)
* **Strong Consistency (Сувора узгодженість):** Забезпечується всередині модуля `Core`. Наприклад, при створенні резервації статус інвентарю оновлюється миттєво в одній транзакції.
* **Eventual Consistency (Узгодженість у кінцевому підсумку):** Реалізована між модулями. Після створення резервації публікується подія `ReservationCreatedEvent`. Модуль `Analytics` оновлює свої лічильники асинхронно через `EventBus`.
* **Переваги:** Це дозволяє системі швидко відповідати користувачу, не чекаючи завершення всіх побічних процесів. Якщо аналітику потрібно буде винести в окремий мікросервіс, механізм подій уже готовий до цього.

## 2. Ретроспектива курсу (Лабораторні 1-5)

### Еволюція архітектури проєкту
* **Лаб 1-2 (Layered Architecture):** Створення фундаменту із розділенням на шари. Це дозволило відокремити БД від логіки.
* **Лаб 3 (CQS):** Розділення читання та запису. Це спростило Handlers і зробило систему більш структурованою.
* **Лаб 4 (Event-Driven):** Впровадження асинхронності (Email, Analytics). Система перестала бути лінійною.
* **Лаб 5 (Modular Monolith):** Фінальне розділення на незалежні контексти з власними моделями даних.

### Найцінніші архітектурні рішення
* **Використання Event Bus:** Це стало ключовим моментом для розв'язання (decoupling) компонентів.
* **Dependency Injection (DI):** Дозволило легко замінювати компоненти (наприклад, перехід від простих сервісів до Handlers).
* **Value Objects та Domain Entities:** Забезпечили валідацію даних на рівні домену, а не лише в БД.

### Висновки та отриманий досвід
1.  **Trade-offs (Компроміси):** Ми побачили, що гнучкість архітектури (ACL, Handlers, DTO) вимагає написання великої кількості "шаблонного" коду (boilerplate). Для маленьких проектів це може бути зайвим, але для систем, що розвиваються — це необхідність.
2.  **Що було б зроблено інакше:** Знаючи фінальну структуру, межі модулів (Bounded Contexts) варто було б закладати ще на рівні Лабораторної №1. Це б значно зменшило обсяг рефакторингу в кінці курсу.
3.  **Готовність до мікросервісів:** Теперішня структура дозволяє винести будь-який модуль в окремий сервіс за лічені години, оскільки комунікація вже побудована на контрактах та подіях.
