Порівняльний аналіз архітектурних рішень: Лабораторна робота №2
1. Зміни в структурі проєкту
У першій лабораторній роботі код був організований за принципом «все в одному», де логіка обробки запитів, валідація та робота з базою даних часто перетиналися в одному шарі. У другій лабораторній роботі проєкт було розділено на чотири чіткі шари відповідно до принципів Clean Architecture:

Domain Layer (Доменний шар): містить чисті бізнес-об'єкти (Entities), інтерфейси репозиторіїв та доменні помилки. Він повністю незалежний від зовнішніх бібліотек (Prisma, Express).

Application Layer (Шар застосунку): реалізує конкретні сценарії використання (Use Cases) через команди (Commands) та запити (Queries).

Infrastructure Layer (Шар інфраструктури): містить технічні деталі — реалізацію репозиторіїв через Prisma та мапери для перетворення даних.

Presentation Layer (Шар представлення): відповідає за HTTP-інтерфейс (контролери та маршрути Express).

2. Переваги розділення на шари
Впровадження шарової архітектури дало наступні переваги:

Ізоляція бізнес-логіки: правила бібліотеки (наприклад, неможливість бронювання зайнятої книги) тепер сконцентровані в доменній фабриці та сутностях, а не в контролерах.

Тестованість: завдяки використанню Dependency Injection, ми змогли написати Unit-тести для домену, підміняючи реальну базу даних моками.

Дотримання DIP (Dependency Inversion Principle): високорівнева логіка (Application) тепер залежить від абстракцій (Repository Interfaces), а не від конкретної реалізації БД.

3. Недоліки та ускладнення
Перехід до складнішої архітектури створив певні труднощі:

Збільшення кількості коду: для реалізації однієї функції (наприклад, видалення) тепер потрібно створити команду, метод у репозиторії, додати логіку в контролер та оновити маршрути.

Необхідність мапінгу: з'явився додатковий код (Mappers) для перетворення об'єктів Prisma у доменні сутності та навпаки.

Складніша навігація: розробнику потрібно перемикатися між багатьма папками та файлами, щоб зрозуміти повний шлях проходження даних.

4. Гнучкість системи
Тепер змінити базу даних (наприклад, перейти з PostgreSQL на MongoDB) або змінити фреймворк (з Express на Fastify) стало значно простіше:

Для заміни БД потрібно переписати лише файли в infrastructure/repositories, не чіпаючи бізнес-логіку.

Для заміни веб-фреймворку потрібно оновити лише presentation шар.

5. Обґрунтування вибору доменної моделі
У проєкті було реалізовано Rich Domain Model (багату доменну модель), оскільки вона краще відповідає принципам Clean Architecture та DDD.

Чому не Anemic Domain Model?
Уникнення «витоку» логіки: в анемічній моделі сутності є лише контейнерами для даних, а вся логіка зосереджена в сервісах (handlers). Це призводить до того, що бізнес-правила «розмазуються» по всьому застосунку, і їх важко контролювати в одному місці.

Запобігання антипатерну Transaction Script: Анемічна модель часто перетворює код на набір процедурних сценаріїв, де сутності втрачають свою роль як «джерела істини».

Переваги обраної Rich Domain Model у нашому проєкті:
Інкапсуляція поведінки: Наші сутності та Value Objects (наприклад, Email) самі відповідають за свою валідність. Об'єкт просто не може бути створений або змінений у невалідний стан, оскільки він сам перевіряє свої прості інваріанти.

Контроль складних інваріантів через Factory: Використання Domain Factory дозволило винести складну логіку, яка потребує доступу до зовнішніх репозиторіїв (перевірка унікальності чи наявності ресурсу), за межі конструкторів, але залишити її в межах Доменного шару. Це дозволяє сервісам застосунку залишатися «тонкими» та займатися лише оркестрацією, а не бізнес-обчисленнями.

Цілісність даних: Оскільки дані та методи роботи з ними знаходяться разом, ми гарантуємо, що будь-яка зміна стану об'єкта (наприклад, статусу в Inventory) відбувається лише за визначеними бізнес-правилами, що унеможливлює появу логічних помилок у базі даних.
